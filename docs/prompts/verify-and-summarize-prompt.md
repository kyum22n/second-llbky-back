# 프롬프트 템플릿: 실행 결과 검증 + 요약 정리

`docs/prompts/db-deploy-setup-prompt.md`의 **1번(DB 연결)**, **2번(배포)** 프롬프트를 실제로 실행한 **이후**에 쓰는 후속 프롬프트입니다.
두 작업은 실행 결과가 그때그때 다르게 나옵니다(전부 성공 / 일부 단계 스킵 / 특정 항목 실패 등). 그래서 "무조건 성공했다고 가정"하지 않고, **실행 결과를 먼저 확인한 뒤 그에 맞춰 검증하고, 결과를 파일로 정리**하도록 설계했습니다.

같은 세션에서 이어서 써도 되고, 실행한 지 한참 지난 뒤 새 세션에서 "그때 한 작업이 지금도 정상인지" 재검증하는 용도로도 쓸 수 있습니다.

---

## 1. DB 연결 결과 검증 + 요약 프롬프트

**언제 쓰나**: `db-deploy-setup-prompt.md` 1번 프롬프트(Neon DB 연결)를 실행한 직후, 또는 그 결과가 지금도 유효한지 재확인하고 싶을 때.

```
db-deploy-setup-prompt.md의 1번 프롬프트(Neon DB 연결)를 실행했어(또는 예전에 실행한 게 있어). 그 결과를 검증하고 요약 문서로 정리해줘.

먼저 확인해줘야 하는 것 (실행 결과가 매번 다를 수 있으니, 아래를 실제로 하나씩 실행/확인해서 성공/실패/스킵 여부를 파악한 다음 그 결과에 맞춰 이어서 진행해줘):

1. 연결 상태
   - 애플리케이션을 기동해서 spring.datasource로 실제 DB(Neon 또는 로컬 Docker)에 연결되는지 확인해줘. 연결 실패면 에러 로그를 보고 원인을 진단해줘 (sslmode 누락, 잘못된 URL 형식, 방화벽/IP 허용 등 — docs/prompts/db-deploy-setup-prompt.md의 3-3 표를 참고해서 매칭되는 항목이 있는지 확인).
2. 스키마 적용 상태
   - docs/db/schema.sql에 정의된 테이블이 실제 DB에 전부 생성됐는지(`\dt` 또는 information_schema 조회로) 확인해줘. 빠진 테이블이 있으면 어떤 스텝에서 실패했는지 원인을 찾아줘.
   - pgvector 확장(`CREATE EXTENSION vector`)이 실제로 활성화됐는지 확인해줘.
   - resume.activities, news_summary.published_at처럼 schema.sql에 "충돌 지점"으로 표시해둔 컬럼들이 실제로 애플리케이션 코드(mapper XML)가 기대하는 이름/타입대로 만들어졌는지 다시 한번 대조해줘.
3. 매퍼 동작 검증
   - 실제로 몇 개의 API를 호출해서(예: 회원가입/조회, 이력서 조회 등 서로 다른 도메인에서 최소 2~3개) MyBatis 매퍼가 정상 동작하는지 확인해줘. 성공/실패 결과를 각각 남겨줘.
   - 3-2에 기록된 기존 버그(interviewQuestion.xml의 insertCustomQuestion, portfolioguide.xml의 deleteAllGuides)를 이번에 실제로 호출해봐서 여전히 문제가 있는지, 혹시 이미 고쳐졌는지 확인해줘.
4. 보안/설정 점검
   - git 이력에 .env, DB 비밀번호, API 키 등이 커밋된 적이 있는지 확인해줘 (`git log -p -- .env` 등으로). 있으면 바로 알려주고, 실제 삭제/롤백은 나와 상의 후 진행해줘.
   - .gitignore가 여전히 민감 파일을 잘 제외하고 있는지 확인해줘.
5. 용량/리스크 재확인
   - Neon 콘솔 기준으로 현재 스토리지 사용량이 무료 티어 한도(약 0.5GB) 대비 어느 정도인지 확인해줘(내가 콘솔에서 직접 캡처해서 알려주면 그 수치를 근거로 판단해줘).

위 확인이 끝나면, 검증 결과는 o/x 표로 정리하고 아래 내용을 담아 docs/db/db-connection-report.md 파일로 정리해줘 (기존 파일이 있으면 갱신):

- 실행 일자, 사용한 DB(예: Neon, 프로젝트명 — 비밀번호/커넥션 문자열 등 민감정보는 절대 포함하지 말 것)
- 적용된 스키마 상태 (전체 테이블 생성 성공 여부, 위에서 발견된 불일치가 있었다면 무엇을 어떻게 고쳤는지)
- 매퍼 스모크 테스트 결과 요약 (성공한 API, 실패한 API와 원인)
- 발견된 신규 이슈 (docs/prompts/db-deploy-setup-prompt.md의 위험 관리 섹션에 없던 것이면 그 내용도 추가해줘)
- 보안 점검 결과 (커밋 이력에 민감정보 없음 확인 등)
- 남은 위험/할 일 (예: 아직 못 고친 버그, 용량 임박 등)
- 다음 단계로 무엇을 하면 되는지 (예: "이제 2번 배포 프롬프트로 넘어가도 됨" 또는 "OO를 먼저 해결해야 함")

주의:
- 검증 과정에서 실제 DB에 손상을 줄 수 있는 명령(DROP, TRUNCATE 등)은 실행하지 말고, 필요하면 먼저 나한테 확인받아줘.
- 확인 결과 문제를 발견했다고 해서 코드나 스키마를 마음대로 고치지 말고, 무엇을 발견했는지와 어떻게 고치면 될지 먼저 보고해줘. 실제 수정은 별도로 요청할게.
```

## 2. 배포 결과 검증 + 요약 프롬프트

**언제 쓰나**: `db-deploy-setup-prompt.md` 2번 프롬프트(Vercel + Render + Neon 배포)를 실행한 직후, 또는 배포된 서비스가 지금도 정상인지 재점검하고 싶을 때.

```
db-deploy-setup-prompt.md의 2번 프롬프트(Vercel + Render + Neon 배포)를 실행했어(또는 예전에 실행한 게 있어). 그 결과를 검증하고 요약 문서로 정리해줘.

먼저 확인해줘야 하는 것 (실행 결과가 매번 다를 수 있으니, 아래를 실제로 하나씩 실행/확인해서 성공/실패/스킵 여부를 파악한 다음 그 결과에 맞춰 이어서 진행해줘):

1. 배포 상태
   - 백엔드(Render)와 프론트엔드(Vercel) 배포가 실제로 성공했는지 각 플랫폼의 대시보드/로그 기준으로 확인해줘. 빌드 실패나 배포 실패가 있었다면 로그에서 원인을 찾아줘.
   - 백엔드 URL과 프론트엔드 URL을 각각 실제로 호출해서(curl 또는 브라우저) 정상 응답이 오는지 확인해줘.
2. 콜드 스타트 실측
   - Render 백엔드가 슬립 상태였다가 첫 요청에서 실제로 얼마나 걸리는지 한번 재봐줘(대략적인 초 단위로). docs/prompts/db-deploy-setup-prompt.md 3-3에 적어둔 "수십 초" 가정이 실제와 맞는지 확인하고, 크게 다르면 문서를 갱신할지 알려줘.
3. 엔드투엔드 검증
   - 프론트엔드(Vercel) → 백엔드(Render) → DB(Neon)로 이어지는 실제 사용자 흐름을 최소 1개 이상 끝까지 실행해줘 (예: 로그인 → 이력서 조회 같은 흐름). 어디서든 끊기면 어느 구간(프론트/백엔드/DB) 문제인지 특정해줘.
   - CORS가 실제로 어떻게 동작하는지 확인해줘 (여전히 전체 허용(`*`)인지, 좁혔다면 Vercel 도메인만 허용되는지).
4. 보안/설정 점검
   - SSLHelper의 SSL 검증 우회 코드가 최종적으로 유지됐는지 제거됐는지 확인하고, 유지됐다면 왜 유지하기로 했는지도 같이 정리해줘.
   - 환경변수가 Render/Vercel 각각에 실제로 등록되어 있고 시크릿이 커밋되지 않았는지 확인해줘.
5. 과금 여부 재확인
   - Render/Vercel/Neon 계정에 결제 수단이 등록됐는지, 등록됐다면 실제로 청구가 발생했거나 발생할 조건에 들어섰는지(무료 한도 초과 임박 등) 각 플랫폼의 사용량/청구 페이지 기준으로 확인해줘(내가 직접 화면을 캡처해서 알려주면 그걸 근거로 판단해줘).
6. 외부 API 사용량
   - OpenAI/Naver/News API/Google Custom Search의 무료 쿼터 대비 현재 사용량이 어느 정도인지 확인 가능한 범위에서 알려줘.

위 확인이 끝나면, 검증 결과는 o/x 표로 정리하고 아래 내용을 담아 docs/deploy/deployment-report.md 파일로 정리해줘 (기존 파일이 있으면 갱신):

- 실행 일자, 최종 배포 URL (백엔드/프론트엔드, 민감정보 제외)
- 배포 구성 요약 (프론트: Vercel / 백엔드: Render Free Web Service / DB: Neon) 및 실제로 이 구성대로 배포됐는지 확인 결과
- 엔드투엔드 검증 결과 (성공한 흐름, 실패했다면 어느 구간에서 왜 실패했는지)
- 콜드 스타트 실측치와 대응 방법(적용했다면 무엇을 적용했는지)
- CORS/SSLHelper 최종 처리 결과와 그 이유
- 과금 관련 확인 결과 (카드 등록 여부, 실제 청구 여부, 무료 한도 대비 사용량)
- 남은 위험/할 일
- 포트폴리오에 바로 쓸 수 있는 한두 문단짜리 프로젝트 소개 초안 (배포 구성, 무료 인프라 제약을 어떻게 다뤘는지 위주로 — docs/prompts/db-deploy-setup-prompt.md 4번 섹션의 "포트폴리오 보완 작업" 문구를 참고해서)

주의:
- 검증 과정에서 실제 운영 배포에 영향을 주는 조작(재배포, 환경변수 변경, 플랫폼 설정 변경 등)은 하지 말고, 필요하면 먼저 나한테 확인받아줘.
- 확인 결과 문제를 발견했다고 해서 코드나 배포 설정을 마음대로 고치지 말고, 무엇을 발견했는지와 어떻게 고치면 될지 먼저 보고해줘. 실제 수정은 별도로 요청할게.
```

## 사용 팁

- 두 프롬프트는 각각 대응하는 실행 프롬프트(1번/2번) **직후**에 쓰는 게 가장 정확합니다. 시간이 지난 뒤에 쓰면 "그때 결과"가 아니라 "지금 시점 재검증"이 되므로, 그 사이에 플랫폼 정책이 바뀌었거나(예: 무료 티어 정책 변경) 무료 DB가 일시정지됐을 가능성까지 같이 확인하게 됩니다.
- 두 프롬프트 모두 "성공했다고 가정하지 말고 직접 확인부터 하라"는 지시를 포함하고 있습니다. 만약 이전 실행이 부분적으로만 성공했다면(예: DB 연결은 됐지만 배포는 아직 안 함), 결과 보고에서 그 사실을 그대로 알려달라고 하면 됩니다.
- 결과 요약 파일(`docs/db/db-connection-report.md`, `docs/deploy/deployment-report.md`)은 매번 갱신하는 방식으로 운영하면, 이 프로젝트의 "현재 상태"를 항상 최신으로 볼 수 있는 단일 문서가 됩니다. 나중에 이력서/포트폴리오 정리할 때도 이 두 파일만 보면 됩니다.
- 두 프롬프트 모두 실제 운영 환경에 영향을 주는 조작은 하지 않고 "확인 + 보고"만 하도록 제한해뒀습니다. 검증 중 발견된 문제를 실제로 고치고 싶으면, 보고받은 내용을 바탕으로 별도 프롬프트로 요청하세요.
